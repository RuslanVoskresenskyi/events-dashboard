## Записи

### 001 — Модель таблиці events
**Рішення:** Таблиця має поля `id`, `user_id`, `event_name`, `occurred_at`, `metadata`  
**Чому:** Мінімально достатньо для аналітики; `metadata` як JSONB дає гнучкість для довільних даних про подію без зміни схеми  
**Що відкинули:** Окреме поле `event_type` — надлишкове, `event_name` вже несе достатньо інформації  

### 002 — Модель таблиці users
**Рішення:** Таблиця має тільки `id` і `username`  
**Чому:** Нашому дашборду більше не потрібно; проєкт аналітичний, не продуктовий  
**Що відкинули:** Телефон — захист від дублювання акаунтів не є нашою задачею; поле `status` — гостьова логіка ускладнила б ідентифікацію між сесіями  

### 003 — Стратегія видалення користувача
**Рішення:** Каскадне видалення — разом з користувачем видаляються всі його події (`ON DELETE CASCADE`)  
**Чому:** Дані симульовані, реального видалення не буде; проста схема без додаткової логіки  
**Що відкинули:** Soft delete з полем `status` — зайва складність у резолверах і фільтрах для навчального проєкту  

### 004 — GraphQL-схема: перелік запитів
**Рішення:** Визначили п'ять GraphQL-запитів для трьох сторінок дашборду з агрегацією на бекенді.

**Схема:**
Дашборд
eventsPerDay: [{ date, count }]
eventsPerType: [{ eventName, count }]
dashboardSummary: { totalEvents, totalUsers }
Дослідник подій
events(userId, eventName, dateFrom, dateTo, limit, offset): [Event]
Сторінка користувача
user(id): { username, events }

**Чому:** Агрегації рахує бекенд — тягнути мільйони сирих рядків на фронт вбило б продуктивність. Схема спроєктована заздалегідь щоб розуміти які дані і в якому форматі потрібні кожній сторінці.  
**Що відкинули:** Підрахунок агрегацій на фронтенді — занадто багато даних по мережі. Повернення всіх подій одразу без пагінації — неможливо на мільйонах рядків.

### 005 — Вибір типу репозиторія
**Рішення:** Обрано Monorepo замість окремого репозиторія для фронта і бека  
**Чому:** Monorepo спрощує запуск усього разом через один docker-compose і один CI pipeline   
**Що відкинули:** Створення окремого репозиторія для бека і фронта так як це ускладнить розробку навчального проекту   

### 006 — Міграції
**Рішення:** Прості SQL файли замість Alembic 
**Чому:** Це тестовий проект, тому простіше і зручніше змінювати структуру бази даних і працювати з ним  
**Що відкинули:** Створення Alembic так як він відстежує міграції, які застосовані, в нашому проекті де ми постійно змінюємо бд і можемо просто дропнути її це зайва складність

### 007 — Змінні середовища 
**Рішення:** винесли всі змінні з чутливими даними до файлу .env
**Чому:** ці змінні не мають бути публічними тому ми винесли їх в окремий файл, який не попаде в основний репозиторій
**Що відкинули:** Створнення двуг різних змінних для бд з однаковим вмістом, це чисте дублювання тому обрали одну назву яка підходить всюди
