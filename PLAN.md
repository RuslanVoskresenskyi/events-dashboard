# PLAN.md — Дашборд аналітики подій

> Навчальний фул-стек проєкт. Мета подвійна: побудувати справжній застосунок
> сучасним стеком **і** розібратися в кожній технології з нуля.
> Я майже нічого з цього ще не знаю — і це нормально. План враховує це.

---

## 1. Що ми будуємо (простими словами)

Веб-застосунок, у якому можна досліджувати **події** — записи про те, що
колись сталося: «користувач №57 зробив дію *click* такого-то числа о такій-то
годині». Таких подій будуть **мільйони**. Вони несправжні — ми згенеруємо їх
самі, тому це й «симуляція великих даних».

Застосунок дає розглядати цю гору даних по-людськи:
- у вигляді **графіків** (скільки подій по днях, які дії найчастіші);
- у вигляді **таблиці**, яку можна фільтрувати й гортати.

Це спрощений родич інструментів продуктової аналітики — дашбордів, де видно
«скільки користувачів зробили те-то». Ми будуємо маленьку, але справжню версію.

**Аналогія.** Уяви величезний журнал на мільйони рядків. Гортати його руками
неможливо. Наш застосунок — розумна обкладинка над цим журналом: показує
зведення зверху, дає фільтри й уміє швидко знайти потрібний шматок, не
захлинаючись від обсягу.

> Домен свідомо нейтральний і легко замінний. За бажання «події» можуть стати
> телеметрією агентів чи подій ігрового світу — структура проєкту від цього
> не зміниться.

## 2. Технологічний стек

| Шар | Технологія | Навіщо саме вона |
|---|---|---|
| Backend | Python + FastAPI (async) | Сучасний, швидкий, асинхронний веб-фреймворк |
| API | GraphQL через Strawberry | Схема будується з типів Python; природно вчить оптимізаціям |
| База даних | PostgreSQL | На ній вчимося індексам і планам запитів |
| Кеш | Redis | Шар кешування для прискорення |
| Frontend | TanStack Start (React) | Сучасний фул-стек React-фреймворк, типобезпечний |
| Тести (back) | pytest | Стандарт для Python |
| Тести (front) | Vitest + Playwright | Юніт/компонентні + e2e |
| Інфраструктура | Docker + docker-compose | Усе піднімається однією командою |
| CI/CD | GitHub Actions | Автоматичні тести на кожен push |
| Навантаження | k6 або Locust | Перетворює оптимізацію на вимірюваний експеримент |

**Важливо про TanStack Start.** Він зараз у статусі Release Candidate:
feature-complete, API стабільний, реліз 1.0 близько. Для навчального проєкту це
норма, але **зафіксуй версії залежностей** і час від часу їх оновлюй — дрібні
зміни API ще можливі. Беремо саме React-версію (вона мейнстрім і інтегрується
з TanStack Query та Router).

## 3. Фінальний результат (визначення «готово»)

Коли все нижче працює — проєкт завершено:

- [ ] Усе запускається **однією командою** (`docker-compose up`): база, кеш,
      backend і frontend разом.
- [ ] Головна сторінка-**дашборд**: картки зведення (усього подій, унікальних
      користувачів), графік «події в часі», графік «розподіл по типах дій».
- [ ] Сторінка-**дослідник подій**: таблиця з фільтрами (дата, тип дії,
      користувач), яку можна гортати — **плавно навіть на мільйонах рядків**.
- [ ] Сторінка **користувача**: відкриваєш конкретного — бачиш його та події.
- [ ] Усе **завантажується швидко** — бо зроблено оптимізації, і є цифри
      «до/після», які це доводять.
- [ ] На кожен `git push` **CI автоматично ганяє тести** (backend і frontend)
      і світиться зелена галочка.

Якщо можеш показати все це комусь і воно працює — ти переміг.

## 4. Складники (що конкретно пишемо)

1. **Модель даних** — з чого складається подія (id, користувач, тип дії, час)
   і користувач. Фундамент усього.
2. **Генератор даних** — скрипт, що засіває в базу мільйони фейкових подій.
3. **API на GraphQL** — список подій з фільтрами; агрегації (підрахунки —
   скільки подій по днях, скільки по типах); користувач з його подіями.
   *Агрегація* = «порахуй і згрупуй», як зведена таблиця в Excel.
4. **Frontend-дашборд** — три сторінки з розділу «готово».
5. **Шар оптимізацій** — вплетений у все вище (див. розділ 6).
6. **Інфраструктура** — Docker, щоб усе піднімалося разом.
7. **Тести + CI** — див. розділ 7.

## 5. Дорожня карта по фазах

Порядок побудований під реальність: архітектурне — спереду, нудний grind
порізаний на дрібні вимірювані шматки, CI й тести заведені рано (щоб не
лишати «полірування» купою в кінці).

### Фаза 0 — Архітектура та кістяк **DONE**
Перш ніж писати логіку:
- накидати system design (схема сервісів, потоки даних);
- спроєктувати модель даних;
- продумати GraphQL-схему «на папері» (які типи, запити, де будуть болючі місця);
- завести кістяк репо: порожній `docker-compose`, **один прохідний тест**,
  **один зелений запуск CI**.

> Мета фази — у перший тиждень побачити зелену галочку CI. Дешевий дофамін,
> який рятує від прокрастинації пізніше.

### Фаза 1 — Фундамент даних **DONE**
- підняти PostgreSQL у Docker;
- написати генератор, що засіває мільйони рядків;
- **зробити базові запити БЕЗ оптимізацій і заміряти їх** — це твій «before».

> Без заміру «до» оптимізації — це віра, а не інженерія.

### Фаза 2 — Вертикальний зріз (не шари!) **DONE**
Не будуємо весь backend, потім весь frontend. Робимо один тонкий **наскрізний**
шматок: один GraphQL-запит → один резолвер → один список на фронті, що реально
показує дані.

> Коли вся система «дихає» наскрізь рано — мотивація тримається.

### Фаза 3 — Розширення API та UI
- більше типів, фільтри, агрегації на бекенді;
- нормальний UI: три сторінки дашборду через TanStack Query/Router.

### Фаза 4 — Лабораторія оптимізацій
Серце проєкту. Деталі — розділ 6.

### Фаза 5 — Тести як страхувальна сітка
Добрати покриття (деталі — розділ 7). В ідеалі тести пишуться **поряд** з кодом
ще з фази 2, а не купою тут.

### Фаза 6 — CI/CD і фініш
Повний pipeline у GitHub Actions: lint → тести → build образів.
За бажання — деплой.

## 6. Лабораторія оптимізацій

**Головне правило:** кожна оптимізація — це **експеримент**, а не «зробив і
забув». Формат кожного:

1. **Гіпотеза** — «думаю, індекс прискорить цей запит, бо…».
2. **Замір ДО** — конкретна цифра (час запиту, p95-затримка).
3. **Зміна** — одна оптимізація.
4. **Замір ПІСЛЯ** — та сама цифра.
5. **Висновок** — спрацювало? на скільки? чому?

> Цей формат перетворює «нудну оптимізацію» на серію маленьких загадок із
> вимірюваним результатом. Саме те, що тримає інтерес.

Орієнтовний список, від найповчальнішого:

- **Індекси в PostgreSQL** + читання `EXPLAIN ANALYZE`. Навчишся бачити, що
  база реально робить під капотом. Must.
- **Пагінація:** offset проти keyset/cursor — і чому друге не деградує на
  глибоких сторінках.
- **Проблема N+1** у GraphQL і її лікування через **DataLoader** (батчинг
  запитів у один). Класика backend-розробки, дуже наочна саме на GraphQL.
- **Кешування в Redis**; пре-агрегація / materialized views.
- **Фронтенд:** віртуалізація списків (TanStack Virtual), prefetch та infinite
  queries, SSR і стрімінг від TanStack Start.
- **Захист GraphQL:** ліміти глибини й складності запиту.

## 7. Тестування

Уяви тести як **піраміду**: знизу багато дешевих швидких, зверху мало повільних.

### Backend (pytest)
- **Юніт** — на бізнес-логіку й резолвери окремо.
- **Інтеграційні** — на GraphQL-запити цілком (запит → відповідь).

### Frontend (Vitest + Playwright)
- **Юніт-тести (Vitest) — основа.** Перевіряють маленький шматок логіки окремо.
  *Приклад:* функція, що перетворює сирі події на дані для графіка — даємо вхід,
  перевіряємо вихід. Швидкі, їх багато.
- **Компонентні тести (Vitest + React Testing Library) — середина.** Малюють
  один компонент і перевіряють поведінку. *Приклад:* по кліку на кнопку фільтра
  викликається потрібна дія; картка показує правильне число. Без браузера й
  бекенду — усе в пам'яті.
- **E2E-тести (Playwright) — вершина.** «End-to-end» = з кінця в кінець.
  Запускають **справжній браузер** і проходять сценарій як жива людина: відкрити
  застосунок, виставити фільтр, переконатися, що таблиця оновилась. Найближче
  до «воно реально працює», але повільні — тому їх мало, лише на ключові
  сценарії.

**Сенс піраміди:** юніт ловлять дрібні баги дешево й швидко; e2e підтверджують,
що вся система разом не розвалилась. Якщо все робити лише через e2e — тести
стануть повільні й крихкі.

## 8. Принципи роботи (щоб не згаснути на середині)

- **Вертикальний зріз понад шари.** Спочатку тонка наскрізна смужка, що працює,
  потім поглиблення. Бачити цілу систему рано — критично для мотивації.
- **CI і тести — рано, не в кінці.** Один зелений тест у перший тиждень.
- **Оптимізація = експеримент** із заміром до/після. Кожна — маленька перемога
  з цифрою.
- **Тести поряд з кодом**, а не фінальним grind-марафоном.
- **Я пишу код сам.** ШІ — наставник, не генератор. Правила — у `AI_RULES.md`.
